# rCore 实验 Lab4 报告

## 一、ch6 问答题

### 1. 在我们的 easy-fs 中，root inode 起着什么作用？

root inode 是 easy-fs 中**根目录对应的 inode**（inode_id = 0，位于磁盘 inode 区的起始位置），是整个文件系统命名空间的门户。它的作用体现在两个层面：

**作为目录的元数据载体**：root inode 的 `DiskInode`（含 size、数据块指针、nlink、类型）描述根目录本身——它指向的数据块按 `DirEntry`（`DIRENT_SZ` 大小）连续存放，记录了根目录下所有"文件名 → inode_id"的映射。整个文件系统的"通过名字访问文件"能力都建立在这张目录表上。

**作为所有路径操作的统一入口**：os 侧通过全局 `ROOT_INODE` 持有它，`open_file`、`find`、`create`、`make_link`（硬链接）、`delete_link`（删除）、`ls`（列目录）等全部以它为起点，按名字逐级下探。内核启动时，`initproc` 与用户程序也都是经由 root inode 从文件系统加载的（`open_file` 找到文件 → 读出 elf 数据）。

一句话总结：root inode 是"名字 → inode"解析链的根节点，承担着文件系统内所有文件被发现、被创建、被链接、被删除的入口职责。

### 2. 如果 root inode 中的内容损坏了，会发生什么？

需要区分"root inode 的元数据损坏"与"根目录目录项内容损坏"两层，两者都会造成严重后果：

**（1）root inode 的 DiskInode 元数据损坏**
- `size` 字段损坏：目录项数量按 `size / DIRENT_SZ` 计算，大小错误会导致 `ls`/`find`/`link`/`unlink` 遍历错误的目录项范围——要么漏看文件，要么越界读到无关数据块并触发 `read_at` 长度断言失败而 panic。
- `direct`/`indirect1`/`indirect2` 数据块指针损坏：目录项读到错误位置，得到乱码文件名；若指针指向被其他文件占用的块，甚至会造成目录项与文件数据互相覆盖。
- `nlink` 损坏：硬链接计数失真，后续 `make_link`/`delete_link` 的计数增减将不再反映真实链接关系，`nlink` 可能错误归零或虚高。

**（2）根目录目录项（DirEntry）内容损坏**
- `inode_id` 字段损坏：`find` 返回错误的 inode 编号，`get_disk_inode_pos` 定位到错误位置，读取到的是另一个文件甚至 inode 区外的数据，后续读写可能**破坏其他文件的内容**。
- 文件名损坏：打开、链接、删除都找不到预期文件，所有依赖路径的系统调用（`open`、`fstat`、`linkat`、`unlinkat`、`exec`、`spawn`）全部失败或行为异常。

**宏观后果**：由于 `initproc` 与所有用户程序都从根目录加载，root inode 损坏会导致系统**无法启动任何用户程序**，直接 panic 停机；即使侥幸运行，文件系统的命名空间也已不可用，涉及文件的操作（文件测试、链接测试、spawn）必然失败。更危险的是，损坏的指针/编号可能引发**错误的数据块释放或覆写**（例如把仍在使用的块当作空闲块回收），造成文件系统级联损坏，波及未损坏的文件。

## 二、ch7 问答题

### 1. 举出使用 pipe 的一个实际应用的例子。

最典型的例子就是 Linux 终端里的 `cat file.txt | wc -l`——用管道统计一个文件的行数：

- 用户在 shell 中输入 `cat file.txt | wc -l`，shell 先创建一根匿名管道，再 fork 出两个进程：
  - `cat file.txt`：读取文件内容，写入自己的 stdout；
  - `wc -l`：从自己的 stdin 读取数据，统计行数并打印。
- shell 把 cat 的 stdout 重定向到**管道写端**，把 wc 的 stdin 重定向到**管道读端**。这样 cat 的输出字节流不落到磁盘，而是直接作为 wc 的输入，实现"边产出边消费"的流式处理。

pipe 在此的作用：cat 和 wc 是两个独立的进程，彼此没有任何耦合，管道充当了二者之间**单向、匿名、字节流**的数据通道。它把"上一个命令的输出"无缝接给"下一个命令的输入"，省去了写中间临时文件的麻烦，也让两个进程可以并发运行——cat 写一段、wc 读一段，管道缓冲区在中间做流量调节（缓冲区满时写端阻塞，空时读端阻塞）。

这类例子在终端里比比皆是：`ls -l | grep "\.rs"`（过滤文件）、`ps aux | grep python`（查找进程）、`sort data.txt | uniq -c`（去重计数）。它们本质都是同一个模式：**一个进程的输出作为另一个进程的输入，多个简单工具通过管道串联成一条处理流水线**。

### 2. 如果需要在多个进程间互相通信，则需要为每一对进程建立一个管道，非常繁琐，请设计一个更易用的多进程通信机制。

一对一管道的问题在于它是**点对点**的：管道连接固定的两个端点，N 个进程要两两通信就得建 O(N²) 根管道，还要为每对连接维护读/写描述符，繁琐且不可扩展。

我设计一个**命名消息队列 + 主题订阅**的通信机制，把"点对点连接"改成"按名字寻址的共享信箱"：

**基本模型**
- 内核维护一张全局队列表，每个队列有一个**字符串名字**。进程无需知道通信对方是谁，只需共享队列名即可通信。
- 队列支持三类操作：
  - `mq_create(name) -> qid`：创建一个命名队列并返回句柄；
  - `mq_send(qid, data, len)`：向队列写一条有长度的**消息**（区别于管道的裸字节流，消息自带边界，接收方一次取一条）；
  - `mq_recv(qid, buf, len)`：从队列取一条消息；队列空时可选**阻塞等待**，也可非阻塞返回。
- 内核数据结构：一张 `HashMap<名字, 消息队列>`，每个队列是一个**环形缓冲区**，并挂一个**等待队列**记录阻塞在发送/接收上的进程，用于唤醒调度。

**多对多与一对多**
- 多个生产者可同时 `mq_send` 到同一个队列，多个消费者可同时 `mq_recv`——天然支持多对多，无需两两建管道。
- 再叠加一层"主题"：允许进程 `mq_subscribe(topic)` 订阅某主题，任何进程 `mq_publish(topic, msg)` 都会把消息分发给所有订阅者——实现**一对多广播**，适合日志、事件通知等场景。

**为什么更易用**
- 通信关系从 O(N²) 条管道降为 O(N) 个队列，按名字共享，动态增减进程都无需改动已有连接。
- 生产者和消费者解耦：发方只认队列名，不关心"谁在收"；收方只认队列名，不关心"谁在发"。
- 消息自带长度与边界，免去了在字节流上自行做协议分帧（如按 `\n` 切分）的麻烦。
- 可阻塞/非阻塞、可广播，能力上覆盖并超出管道（字节流、一对一、单向）的应用范围。

**与管道的对比**：管道 = 匿名 / 点对点 / 字节流 / 单向；命名消息队列 = 有名 / 多对多 / 消息化 / 可广播。它把"手动为每一对进程接线"的负担，转移给内核统一管理的"信箱"，让进程间通信变得像寄信、收信一样简单。
