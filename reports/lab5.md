# rCore-Tutorial Lab5（ch8）实验报告

## 一、功能总结

本次实验在既有线程模型与同步原语（MutexSpin、MutexBlocking、Semaphore、Condvar）基础上，完成了进程级**死锁检测**：新增 `sys_enable_deadlock_detect` 系统调用，按进程开启检测；阻塞式互斥锁与信号量的等待系统调用在执行阻塞前先做可达性分析，递归判断资源持有者能否继续推进，若各等待方彼此成环、无法进展即判定死锁；命中时不再阻塞，而是返回 `-0xdead`，让用户程序感知并自行恢复。为支撑检测，Mutex 记录当前持有者、Semaphore 记录持有者队列、TCB 记录等待目标（阻塞前设置、唤醒后清除）。全部改动均通过静态符号链与差异核验，未做本地编译。

## 二、问答题

### 1. 主线程（0 号线程）退出时的资源回收

**需要回收的资源：**

- **进程级**：PCB 从进程表与 `pid2process` 中移除，PID 归还分配器；进程地址空间 `MemorySet` 与其页表销毁；用户态资源（用户栈、trap 上下文所在的物理帧）通过 `TaskUserRes` 释放；每个线程的内核栈 `KernelStack` 归还；文件描述符表 `fd_table` 关闭全部打开文件；从父进程的 `children` 中移除本进程，并将孤儿进程重新交给 init 进程管理。
- **线程级**：进程管理的所有子线程的 TCB，连同各自的内核栈、用户栈等资源一并回收。

**其他线程的 TaskControlBlock 可能在哪些位置被引用、是否需回收：**

| 引用位置 | 是否需要回收 | 原因 |
|---|---|---|
| 进程的 `tasks` 向量（`ProcessControlBlockInner.tasks`） | 需要 | 这是进程持有全部线程的权威位置，主线程退出时须清空，否则 TCB 与其资源永不释放 |
| 就绪队列（`TaskManager.ready_queue`） | 需要 | 调度器以 `Arc` 引用持有就绪线程；若不清除，这些线程仍会被调度运行一个已退出进程的地址空间，造成悬垂访问，且 Arc 计数阻止 TCB 释放 |
| 同步原语的等待队列（Mutex / Semaphore / Condvar 的 `wait_queue`） | 需要 | 阻塞线程的 TCB 被同步对象持有；若不处理，它们将永久阻塞、引用泄漏，而所等待的资源随进程消亡永不再来 |
| 处理器当前字段（`processor.current`） | 不需要 | 此处只指向正在运行的主线程本身，退出后由调度切换自然释放，无需额外处理 |

### 2. 两种 Mutex 实现的区别及潜在问题

**区别：**

- **锁释放（解锁）时机**：`Mutex1::unlock` 无条件先置 `locked = false`，再唤醒队头等待者；`Mutex2::unlock` 仅当等待队列为空时才置 `locked = false`，否则直接唤醒队头并把锁“移交”给它（锁始终保持“被占用”状态）。
- **被唤醒线程的行为**：`Mutex1::lock` 使用 `loop`，线程被唤醒后回到循环开头重新检查并**重新竞争**锁；`Mutex2::lock` 不使用循环，被唤醒线程直接认为已获得锁（与 unlock 的移交语义相配合）。
- **公平性**：`Mutex2` 是“锁移交 + FIFO”，队头等待者必定拿到锁；`Mutex1` 是“释放 + 重新竞争”，先释放再唤醒。

**可能导致的问题：**

- **Mutex1**：unlock 先释放锁再唤醒，被唤醒线程需要重新竞争。若在被唤醒线程恢复运行前，已有其他（可能更高优先级或刚新到的）线程抢先取得锁，被唤醒线程只能再次入队阻塞——即使它排在 FIFO 前面也拿不到锁，可能造成**不公平乃至饥饿**，并伴随反复的无效唤醒开销。
- **Mutex2**：等待队列一直非空时，锁始终不进入空闲状态、只在等待者之间移交。此时依赖“被唤醒的队头线程必定真正接管锁”这一前提；若队头线程被唤醒后因异常被结束或未能正确取得锁，锁会**滞留**在 `locked = true` 却无人持有的状态，使其余线程永久等待。
